# AI Agent Distribution & Packaging Patterns Across Ecosystems

*Internal packaging-patterns retrospective, prepared by comparing five active
agent/skill distribution ecosystems: Hermes Agent, LangChain Hub, CrewAI,
OpenAI Assistants, and the MCP Registry. Some specifics below (exact field
names, numeric limits) are illustrative composites assembled for this
retrospective rather than a line-by-line audit of live vendor docs — verify
against current documentation before treating any single number as
authoritative in a production decision.*

## 1. Scope and method

We looked at how each ecosystem answers three questions: what does a
publishable unit's manifest actually declare, where is the line drawn between
data the distributor/publisher owns and data the installing user owns, and
how (if at all) does the packaging format keep secrets out of what gets
published. We also kept a running list of risks that came up repeatedly
across ecosystems but that none of the five have actually solved yet.

The five systems compared:

- **Hermes Agent** — bundles a full agent (chat/tool/cron entrypoints) as a
  signed archive, published to a Hermes-run registry.
- **LangChain Hub** — publishes individual serialized objects (prompts,
  chains, agent graphs), or small groups of them, under an owner/repo handle.
- **CrewAI** — distributes a "crew" (a set of role-based agents plus tasks)
  as a project folder or tarball, usually via git rather than a registry.
- **OpenAI Assistants** — the Assistant itself is a live API object owned by
  a workspace; portability is handled entirely by third-party export/import
  tooling, not a first-party manifest.
- **MCP Registry** — indexes MCP servers (tool/resource providers), which are
  distributed through existing package registries (npm, PyPI, Docker) and
  merely *referenced* by the MCP registry's own manifest.

## 2. Manifest design across five ecosystems

### 2.1 Overview table

| Ecosystem | Manifest file | Versioning | Entrypoint declaration | Signing/checksum |
|---|---|---|---|---|
| Hermes Agent | `hermes.manifest.yaml` | strict semver, immutable per version | `entrypoints` map (chat/tool/cron → handler path) | `hermes.lock` sha256 + publisher key fingerprint |
| LangChain Hub | `hub_manifest.json` (multi-object) or none (single object) | `major.minor` only, not enforced | implicit — object `type` field (prompt/chain/agent/tool) | none |
| CrewAI | `crew.yaml` | free-string `crew_version`, not validated | implicit — `process` field (sequential/hierarchical) plus `agents[]`/`tasks[]` | none |
| OpenAI Assistants | de facto `assistant.json` (third-party export format) | none — live object, no version field | `tools[]` declares tool types; no separate entrypoint concept | none (workspace auth is the boundary) |
| MCP Registry | `server.json` | semver, per-package | `packages[]` per distribution channel (npm/pypi/docker) | none at the registry-manifest level; delegated to the underlying package registry |

### 2.2 Hermes Agent

The manifest lives at the root of a `.hermes` bundle (effectively a zip).
Required keys: `id` (reverse-DNS style, e.g. `com.example.support-triage`),
`version` (strict semver — the registry rejects any attempt to re-publish an
already-used version number, so versions are immutable once published),
`entrypoints` (a map from trigger type to handler path — `chat`, `tool`,
`cron`), `capabilities` (a flat list of tags used for registry search and
filtering), `runtime` (language plus a pinned version, e.g. `python:
"3.11"`), `secrets_schema` (a list of required secret *names*, each with a
`description` and a `required` boolean — the publish CLI rejects the whole
manifest if any `secrets_schema` entry also carries a `value` key, so a
literal secret can't even be declared in the schema by mistake), `data_scope`
(covered in section 3), `checksum`, and `publisher_key_fingerprint`. The
checksum itself is *not* stored inside the manifest — it lives in a
companion `hermes.lock` file generated by the publish CLI, specifically so a
hand-edited manifest can't claim a checksum for a bundle it doesn't actually
match. Deprecation is a separate registry call
(`hermes.deprecate <id>@<version>`), not a manifest field.

### 2.3 LangChain Hub

The distribution unit is usually a single serialized object — a prompt, a
chain, or an agent graph — identified by an `owner/repo_name` handle and a
content hash rather than a manifest file. When several objects are grouped
together, a `hub_manifest.json` at the root lists an `objects[]` array, each
entry carrying a `path`, a `type` (`prompt` | `chain` | `agent` | `tool`),
and an `lc_version` compatibility range. `hub_version` uses a bare
`major.minor` scheme, predating the rest of the ecosystem's adoption of full
semver, and nothing in the Hub's own tooling actually validates or enforces
it — a publisher can push `"1.0"` after `"2.3"` and nothing stops them.
There is no `secrets_schema` field of any kind. The working convention —
never enforced by any validator — is that a serialized object must never
carry a literal value pulled from `os.environ`, and that any credential the
object needs should instead be *named* in the object's free-text `readme`
field. Because that field is free text, nothing stops an author from pasting
a literal key into it too; the convention relies entirely on author
discipline.

### 2.4 CrewAI

A crew is distributed as a `crew.yaml` plus its project folder, usually via
a git repository, sometimes packaged into a `.crewpack` tarball. Manifest
fields: `crew_name`, `crew_version` (nominally semver, but the field is a
free string CrewAI's own tooling does not validate), `agents[]` (each with
`role`, `goal`, `backstory`, and an `llm` reference), `tasks[]`, `process`
(`sequential` or `hierarchical`), and `memory` (a boolean plus an optional
`memory_backend`). Credentials are referenced through `${ENV_VAR}`
interpolation syntax anywhere in the YAML, resolved by the CrewAI runtime at
crew-run time — but because the field holding that string is just plain
YAML, the schema itself cannot distinguish an interpolation reference from a
literal value. A validator that only checks "does this crew.yaml parse and
match the schema" cannot tell a clean crew.yaml from one with a hardcoded
key sitting in an `llm:` override; catching that requires a separate
raw-text scan for secret-shaped strings, which is outside the schema
entirely.

### 2.5 OpenAI Assistants

By design there is no checked-in manifest — an Assistant is a live API
object that belongs to a workspace. Portability is handled entirely by
third-party tooling, which has converged informally on a portable
`assistant.json` export format with `name`, `instructions`, `model`,
`tools[]`, `tool_resources` (pointers to vector-store IDs and file IDs —
these are workspace-scoped *references*, not embedded file content, so
exporting an `assistant.json` never copies any file's actual bytes), and
`metadata` (a free-form key-value map, commonly documented with practical
limits in the neighborhood of 16 pairs / 64-character keys / 512-character
values — treat this specific figure as illustrative and confirm against
current API documentation rather than relying on it here). Because
`tool_resources` only ever contains IDs, moving an `assistant.json` into a
different workspace requires a separate re-upload step for every file the
assistant actually depends on; the manifest alone is not portable on its
own.

### 2.6 MCP Registry

The distribution unit is `server.json`, submitted to a registry index for
an MCP server (a tool/resource provider, not a full agent). Fields: `name`
(namespaced, e.g. `io.github.org/server-name`), `version` (semver),
`description`, `packages[]` — one entry per distribution channel (npm, pypi,
docker), each carrying its own `identifier` and `version` — and an optional
`remotes[]` array for hosted/remote server endpoints. There is no dedicated
secrets field anywhere in the registry-facing manifest; any environment
variables the server needs at runtime are documented only in prose, in the
`description` or an external README. Of the five ecosystems studied, this is
the weakest with respect to secret handling, because there isn't even a
structured place to enumerate a secret's *name* the way Hermes and (in
convention only) LangChain Hub do — let alone anything that would stop a
value from being committed alongside it.

### 2.7 Cross-cutting observations

Only two of the five (Hermes, MCP Registry) enforce real semver with
registry-side validation. Only one (Hermes) makes versions immutable at the
registry level. Only one (Hermes) signs the bundle against a
registry-verified publisher key; the other four rely entirely on
registry-account identity, which is only as strong as that account's own
authentication. None of the five have a manifest field that says "this
package supersedes version X" or "install this instead" in a machine-readable
way — deprecation, where it exists at all, is either a side-channel API call
(Hermes) or a prose note in a README (everyone else).

## 3. Distributor-owned vs. user-owned data separation

### 3.1 The distinction

*Distributor-owned* data is anything that belongs to the publisher or the
registry itself and doesn't change per install: the package identity and
version, the publish timestamp, the publisher's identity and signature,
aggregate download/install counts, aggregate ratings, moderation/
verification status, and the registry's own audit trail. *User-owned* data
is anything that belongs to whoever installed the package and is specific to
their own use of it: local configuration overrides, per-user credentials and
secrets, conversation or session history, any locally cached memory or
embeddings, usage/cost logs tied to the user's own account, and any content
the user supplies at runtime (uploaded documents, fine-tuning data, files
fed into a vector store).

| Category | Distributor-owned example | User-owned example |
|---|---|---|
| Identity | package id, version, publisher signature | local install path, per-user API keys |
| Usage data | aggregate download/install counts | individual session/conversation logs |
| Content | shipped default prompts/templates | user-provided documents, fine-tune data |
| Configuration | schema and defaults declared in the manifest | resolved runtime values, environment variables |

### 3.2 Where the line blurs

Two recurring failure patterns showed up across ecosystems. First, a
manifest or exported config that embeds a "default" resource pointer that
actually resolves to the *publisher's own* private data — for example, an
`assistant.json` whose `tool_resources` still points at the original
author's vector store ID rather than a placeholder, so every downstream
install that doesn't manually swap the ID ends up querying the publisher's
private content instead of the installer's own. Second, a registry that
stores per-user analytics (who installed what, when) in the same record as
the package's own public metadata, which entangles two things that should be
deletable independently — removing "the package listing" and honoring one
user's request to delete "my installation record" become the same
operation instead of two, which complicates any deletion or export request
that only concerns one side.

### 3.3 Per-ecosystem notes

Hermes Agent is the only one of the five that formalizes this distinction
directly in the manifest, via a `data_scope` object with two keys —
`distributor` and `user` — each listing what that side is expected to own.
LangChain Hub doesn't formalize it at all: a shared prompt or chain object
is distributor-owned by construction, since nothing in a bare prompt
template is user-specific, but once someone customizes and republishes a
fork, there's no documented answer for whose data the fork's differences
are. CrewAI's `memory_backend` setting determines *where* user-side
conversation memory is stored, but the manifest doesn't mark that
configuration as distinct from the crew definition itself — both live in
the same `crew.yaml`. OpenAI Assistants keeps this reasonably clean by
construction, since `tool_resources` are workspace-scoped references rather
than embedded content, but the "stale default vector store" failure mode
above is a real, observed exception to that cleanliness. MCP Registry has
essentially no user-data concept at the manifest level at all, because an
MCP server's own runtime storage is entirely outside anything the registry
manifest describes.

## 4. Secrets exclusion patterns

The rule that held across every ecosystem worth taking seriously, stated
plainly: a manifest may declare that a secret is required. It may never
declare what that secret's value is. Enforcement of that rule, however,
varies enormously.

Hermes Agent enforces it in two layers: the schema itself only allows a
secret *name*, `description`, and `required` flag (no `value` key is even a
valid field, so the manifest can't structurally hold a literal secret), and
the publish CLI additionally runs a static high-entropy-string scan across
the *entire* bundle — not just the manifest — before accepting a publish,
so a literal key accidentally left in some other file (a filled-in
`.env.example` that was supposed to stay a template, for instance) also
blocks the publish. LangChain Hub has no enforcement at all — the
env-var-name-in-the-readme convention described in section 2.3 is honor
system only. CrewAI's `${ENV_VAR}` interpolation is a runtime convenience,
not a schema constraint; nothing in `crew.yaml`'s structure prevents a
literal value from sitting in the same field a reference belongs in, so the
only real defense available to CrewAI-side tooling is a raw-text scan over
the YAML, same as the gap already noted in section 2.4. OpenAI Assistants
mostly avoids the problem at the manifest level, since the assistant object
itself doesn't typically declare model-provider secrets — the caller's own
API key authenticates the request, not the assistant object — but
third-party `tool_resources` extensions that wire in custom tool
integrations reintroduce the same class of risk in their own, separate
configuration. MCP Registry is the weakest of the five here, for the same
reason noted in section 2.6: there is no schema field for secrets at all, so
there isn't even a place to *name* a required secret, let alone anything
that would stop a value from being committed next to it.

One case worth recording in detail: a widely forked CrewAI starter template
(tracked internally as ticket OPS-2291) shipped with a literal
`OPENAI_API_KEY` value sitting in an `llm:` override field instead of the
usual `${OPENAI_API_KEY}` interpolation reference — the result of a rushed
demo edit made the night before a conference talk. The fork was starred and
cloned more than 400 times before the key was rotated three days later. The
postmortem's stated takeaway was that before merging any forked template
change on a Friday afternoon, the raw-text secret scanner should always run
across the *entire* diff, not only the files that had changed since the
last scan — the leak in this case sat in a file the incremental scan had
already marked clean from an earlier pass.

## 5. Checklist of unsolved risks

None of the five ecosystems studied have solved every one of these. Listed
roughly in the order they came up during the comparison, not by severity.

1. **Namespace collision across registries.** There's no ecosystem-independent
   way to confirm that `example-org/support-agent` on LangChain Hub and
   `com.example.support-agent` on Hermes belong to the same publisher. A
   registry that doesn't verify domain or account ownership before granting
   a name leaves room for a lookalike registration.
2. **No standard revocation signal.** Pulling a compromised version from a
   registry's own index doesn't propagate to mirrors, forks, or already-
   cached local copies. Only Hermes has a revocation-style call at all
   (`hermes.deprecate`), and even that doesn't force an already-downloaded
   bundle to stop running.
3. **No cross-ecosystem secret-rotation signal.** If a required secret is
   compromised, none of the five have a built-in way to notify every
   existing install "rotate this now" — it has to happen out-of-band, if it
   happens at all.
4. **Inconsistent versioning semantics.** Hermes and MCP Registry enforce
   real semver; LangChain Hub uses an unenforced major.minor scheme; CrewAI's
   version field is a free string nothing validates. "Compatible version"
   doesn't mean the same thing when compared across ecosystems.
5. **Uneven supply-chain provenance.** Only Hermes signs a bundle against a
   registry-verified publisher key. The other four rely entirely on
   registry-account identity, which is only as strong as that account's own
   authentication.
6. **Dependency-confusion exposure.** Both CrewAI and LangChain Hub let a
   local, unpublished object or crew shadow a registry name during
   development. If someone else later publishes that same name to the
   registry first, existing local setups can silently start resolving to
   the wrong — potentially malicious — remote object instead of the local
   one they were built against.
7. **No mechanical license propagation.** None of the five validate that a
   redistributed fork retains or declares the original package's license.
   It's a documentation convention everywhere, enforced nowhere.
8. **Undocumented telemetry/privacy boundary outside Hermes.** Per section 3,
   only Hermes formalizes distributor-owned vs. user-owned data in the
   manifest itself. For the other four, honoring a deletion or export
   request requires manually tracing, per registry, what's actually stored
   where.
9. **Registry verification doesn't cover remote-hosted behavior.** MCP
   Registry's `remotes[]` field can point at a hosted endpoint the registry
   itself never inspects — the registry validates the manifest, not the
   behavior of a remote server it merely links to. Being listed implies
   nothing about the content or behavior of a remote-hosted entry.
10. **No guaranteed migration path on deprecation.** A deprecated Hermes
    version, or a deprecated Hub object, may amount to nothing more than a
    prose note in a README. None of the five manifests have a
    machine-readable "use this instead" field.
11. **No standard trust tier between "schema-valid" and "behavior-reviewed."**
    A syntactically valid, correctly signed manifest says nothing about
    whether the code it ships is actually safe to run — schema validation
    and security review are two different questions, and none of the five
    label which one (if either) a given listing has actually had.
