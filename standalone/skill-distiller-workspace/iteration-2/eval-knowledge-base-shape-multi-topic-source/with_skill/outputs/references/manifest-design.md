# Manifest design across five distribution ecosystems

Load this when designing a new manifest/schema for a package, skill, or
agent registry, or when reviewing/comparing an existing one against how
Hermes Agent, LangChain Hub, CrewAI, OpenAI Assistants, and MCP Registry
each handle the same problem.

Caveat: field names and behavior below reflect a synthesized comparative
retrospective, not a verified audit of current vendor documentation —
confirm specifics against live docs before relying on them operationally.

## Snapshot

| Ecosystem | What gets published | Manifest | Version enforcement | Provenance |
|---|---|---|---|---|
| Hermes Agent | a full agent bundle (chat/tool/cron) | `hermes.manifest.yaml` | strict semver, immutable per version | bundle signed, publisher key verified by registry |
| LangChain Hub | one serialized object, or a small group | `hub_manifest.json` (group only) | `major.minor`, unenforced | none |
| CrewAI | a role-based crew (agents + tasks) | `crew.yaml` | free string, unvalidated | none |
| OpenAI Assistants | a live workspace-owned API object | de facto `assistant.json` (third-party export) | none — no version concept | workspace auth only |
| MCP Registry | an index entry referencing external packages | `server.json` | semver, per referenced package | delegated to the underlying npm/pypi/docker registry |

Two ecosystems (Hermes, MCP Registry) treat version numbers as something the
platform itself checks. The other three treat versioning as a label the
author chooses, with no registry-side guarantee it means anything
consistent — which matters any time you're trying to reason about
"compatible version" across more than one of these systems at once: the
phrase doesn't carry the same guarantee everywhere it's used.

## What each manifest actually declares

**Identity and namespace.** Hermes uses a reverse-DNS-style `id`
(`com.example.support-triage`); MCP Registry uses a similar namespaced
`name` (`io.github.org/server-name`); LangChain Hub uses a flat
`owner/repo_name` handle; CrewAI has no registry-level namespace at all
since distribution is typically git-based rather than through a shared
index; OpenAI Assistants has no manifest-level namespace because the object
lives inside one workspace and was never designed to be looked up by name
across workspaces.

**Entrypoints / shape of the unit.** Hermes is explicit — an `entrypoints`
map from trigger type (`chat`, `tool`, `cron`) to a handler path. The other
four only imply their shape through other fields: LangChain Hub's `type`
per object (`prompt`/`chain`/`agent`/`tool`), CrewAI's `process` field
(`sequential`/`hierarchical`) combined with its `agents[]`/`tasks[]` lists,
OpenAI Assistants' `tools[]` array, and MCP Registry's `packages[]` array
(one entry per distribution channel — npm, pypi, docker — each with its own
`identifier` and `version`).

**Credential requirements, structurally.** Only Hermes gives credentials
their own schema object (`secrets_schema`: a list of names, each with a
`description` and a `required` flag, with no `value` key even accepted as
valid). Everyone else either relies on convention (LangChain Hub, CrewAI) or
has no field for it at all (OpenAI Assistants, MCP Registry). Full detail in
`secrets-exclusion.md` — this file only covers the shape of the field, not
how well it's enforced.

**Data-ownership fields.** Only Hermes has one: `data_scope`, an object with
`distributor` and `user` keys, each a list of what that side is expected to
own. See `data-ownership-separation.md`.

**Resource references vs embedded content.** OpenAI Assistants'
`tool_resources` field is worth calling out specifically: it holds only
vector-store and file *IDs*, scoped to the exporting workspace — never the
files' actual bytes. That makes an `assistant.json` export non-self-
contained: reusing it in a different workspace requires re-uploading every
file it depends on, even though the manifest itself transfers cleanly.
`metadata` on the same object is a free-form key-value map, commonly
documented with limits in the range of 16 pairs / 64-character keys /
512-character values — treat that figure as illustrative for this
comparison rather than a confirmed current spec.

## Enforced vs. merely documented

This is the single most useful lens for auditing any of these manifests, or
designing a new one: for every field, ask whether a validator actually
checks it, or whether it only works because authors happen to follow the
convention.

- **Enforced by schema or registry:** Hermes's `secrets_schema` (no `value`
  key permitted), Hermes's version immutability, Hermes's checksum-vs-bundle
  match (checksum lives in a separate `hermes.lock`, generated by the
  publish tooling, specifically so a hand-edited manifest can't assert a
  checksum that doesn't match what it actually ships), MCP Registry's and
  Hermes's semver format.
- **Convention only, unchecked by any validator:** LangChain Hub's
  "don't put `os.environ` values into a serialized object," CrewAI's
  `${ENV_VAR}` interpolation pattern, LangChain Hub's `major.minor`
  ordering, CrewAI's `crew_version` field in general.
- **Structurally impossible to check from the manifest alone:** whether a
  plain string field (CrewAI's `llm:` override, LangChain Hub's `readme`)
  holds a reference or a literal value — the schema can't distinguish them;
  only a raw-text scan over the actual file content can.

## Takeaways for designing a new manifest schema

- If a field is meant to hold a *reference* (to a secret, to a resource, to
  another package), make that structurally distinct from a field that could
  hold a literal — a separate `*_ref` field or a schema type the value must
  match, not just a naming convention a validator can't check.
- Store integrity/provenance data (checksums, signatures) outside the
  manifest the author edits, generated by the publish tooling itself — the
  same reason Hermes keeps its checksum in `hermes.lock` rather than in
  `hermes.manifest.yaml`.
- Decide up front whether version strings are registry-enforced semver or
  an author-chosen label, and say so explicitly in the schema — don't leave
  it ambiguous the way CrewAI's `crew_version` and LangChain Hub's
  `hub_version` currently are.
- If the unit being distributed can reference external resources (files,
  vector stores, other packages), design those references to be
  re-scopable per install from the start — see
  `data-ownership-separation.md` for what happens when they aren't.
