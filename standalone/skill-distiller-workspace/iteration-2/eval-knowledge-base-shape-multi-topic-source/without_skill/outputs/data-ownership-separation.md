# Distributor-Owned vs. User-Owned Data

Reference for: deciding what an install/upgrade/rollback/uninstall is allowed to touch, and reviewing whether an existing package format gets this right.

## The distinction

**Distributor-owned data** defines the agent's identity and default behavior: the base system prompt, default tool bindings, example few-shot transcripts, default model parameters, and the manifest itself. It is immutable from the user's perspective except through an explicit override mechanism, and it is exactly what an `upgrade` operation is supposed to replace.

**User-owned data** is anything generated by *using* the agent: conversation history, long-term memory entries, learned preferences, per-user credential bindings, fine-tuned prompt overrides, telemetry, and — in RAG-heavy setups — any knowledge base content the user uploaded themselves (as opposed to the one the package shipped with).

The single most consequential design decision in an agent package format is where this line falls, and whether it is enforced structurally or left to convention. Get it wrong and either (a) an upgrade silently wipes a user's memory/history, or (b) a redistributed package accidentally carries one user's private data to another installer.

## How each ecosystem handles it

- **Hermes Agent — strongest separation, structural.** Package contents install into `~/.hermes/packages/<name>/<version>/`, read-only after install and content-addressed by hash. User state lives entirely under `~/.hermes/state/<name>/` in a separate SQLite file the installer never touches. Upgrade = replace the package directory wholesale, state untouched. Rollback = repoint to the previous version directory. This is the cleanest of the five because Hermes was designed after the other ecosystems had already exposed the failure modes below.

- **CrewAI — essentially no separation.** A crew's YAML defines agents and tasks; persistent memory (CrewAI supports short/long-term memory backed by a local vector store) lives in a project-local `.crewai/` directory not distinguished from the crew definition in version control unless a team manually gitignores it. Consequence observed in practice: teams redistributing crews frequently ship accumulated memory state by accident, leaking one customer's task history into a template shared with another team.

- **LangChain Hub — avoids the problem by having no durable state in the base artifact.** A pulled prompt or chain is stateless until wired into the caller's own memory/store implementation, so the ownership line is pushed entirely onto the integrating application. Simpler, but the Hub cannot express "this chain expects memory to persist across sessions" — that contract lives in documentation, not the manifest.

- **OpenAI Assistants — blurs the line by design.** The assistant object (distributor-owned in spirit) and thread objects (unambiguously user-owned, containing conversation history) are both server-side OpenAI resources. The trap: file-search vector stores can be attached at the *assistant* level (intended as distributor-owned reference knowledge shipped with the template) or at the *thread* level (user-owned, per-conversation upload). Templates that hardcode a specific `vector_store_id` at the assistant level bake one tenant's private documents into a "reusable" template — a real cause of data-leak incidents when teams clone an assistant config between environments without re-scoping the vector store reference.

- **MCP Registry — sidesteps most of the problem, unevenly.** MCP servers are typically stateless from the registry's point of view; persistent state, if any, is the server implementation's own concern, entirely outside the manifest. This makes MCP Registry manifests the least likely of the five to leak user data through the package itself, but server authors get no registry-level guidance or enforcement on where to put state, so separation quality varies enormously project to project.

## Recommended pattern for new designs

- Treat distributor-owned data as **content-addressed and read-only post-install**: hash it, and refuse to load if the runtime hash doesn't match what the manifest declares.
- Put **all** user-owned data in a physically separate directory or storage namespace.
- No install/upgrade/uninstall operation should ever write to the user-owned namespace except through an explicit, user-confirmed "reset" action.
- Never let a single directory (or a single object, as in the Assistants vector-store trap) hold both distributor-owned and user-owned data — if a field *can* be filled with either depending on context (like `vector_store_id`), document and enforce which one is expected at which attachment point, and validate against it.

## Fast diagnostic questions

- If I run "upgrade," what on disk (or server-side) changes? Can I predict this from the manifest alone, or do I have to read the runtime's install code?
- If I redistribute this package to a teammate exactly as I received it after using it for a week, does anything of *mine* travel with it?
- Is there any single field or object whose ownership depends on where in the system it's attached (like Assistants' vector store) rather than on its type? If so, that field is the highest-risk spot for accidental data leakage.
