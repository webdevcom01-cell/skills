# Agent Distribution Patterns

Packaging an AI agent differs from packaging a library: the artifact carries behavior (a prompt/role that becomes part of what the model does), tool/capability bindings, and often a claim on user data (memory, credentials, history) that must survive across versions. Four concerns recur across every agent registry and need separate treatment — bundling them into one file loses detail on each, so they live in their own reference below.

## When to use this skill

- Designing a new manifest/package format for an agent, crew, prompt, or MCP server.
- Writing or reviewing a manifest for an existing ecosystem (Hermes Agent, LangChain Hub, CrewAI, OpenAI Assistants, MCP Registry, or something structurally similar).
- Deciding what an "upgrade" is allowed to touch vs. what it must leave alone (memory, credentials, per-user overrides).
- Making sure a package about to be published contains no literal secrets.
- Doing a pre-publish or pre-install risk pass on an agent package.

## How to use the references

Load only what the current task needs — each file stands alone.

1. **`manifest-design.md`** — what fields a manifest needs (identity, compatibility, capabilities, behavioral payload, data references, permission scopes), a worked minimal schema, and how the five reference ecosystems differ. Start here when designing or reviewing a manifest's shape.
2. **`data-ownership-separation.md`** — the distributor-owned vs. user-owned data line: what an upgrade may overwrite, what it must never touch, and how each ecosystem enforces (or fails to enforce) that boundary. Start here when the question is "what happens to existing state on update/rollback/uninstall."
3. **`secrets-exclusion.md`** — the four-tier strength model for keeping secrets out of a package (structural type-level exclusion → scanning → documentation-only → platform custody) plus a concrete pre-publish checklist. Start here before publishing anything, or when reviewing whether a manifest format even *can* hold a literal secret.
4. **`unsolved-risks-checklist.md`** — a checkbox list of risks with no consistently adopted fix industry-wide (namespace squatting, late-bound capability disclosure, prompt injection via registry content, transitive permission escalation, no standardized revocation, provenance gaps, no sandboxing standard, telemetry secret leakage, licensing ambiguity, cross-ecosystem portability). Run this checklist before adopting a third-party package or before telling a team a package format is "safe by design."

## Quick orientation across the five ecosystems

| Ecosystem | Distribution unit | Manifest strength | Secrets model |
|---|---|---|---|
| Hermes Agent | signed `.hermes` bundle | strong (typed, signed) | structural (name-only, install-time resolve) |
| LangChain Hub | prompt/chain artifact | weak (content registry, no code) | documentation-only |
| CrewAI | crew repo (`agents.yaml`+`tasks.yaml`) | weak (no standard manifest) | documentation-only |
| OpenAI Assistants | server-side assistant object | platform-owned (implicit) | platform custody (assistant is clean; tool-call creds are the developer's problem) |
| MCP Registry | `server.json` + launch command | moderate (identity/compat only; capabilities late-bound) | scanning at publish time |

Use this table to route a specific question fast; use the four reference files when the answer needs the reasoning, not just the row.

## Core principle to carry into any new design

Two structural choices predict almost everything else about how safe a package format turns out to be in practice:

- **Data references, not data.** A manifest field should hold a pointer (an env var *name*, a resource URI, a secret-manager *key path*) — never a resolved value. If the field's type allows a literal secret or a literal blob of another tenant's data, it will eventually contain one.
- **Separate storage for what ships vs. what accumulates.** Content-address and make read-only anything the distributor ships (prompt, default config, manifest). Put anything generated by *using* the agent (memory, history, per-user credential bindings) in a physically distinct location that install/upgrade/uninstall never writes to except on an explicit, user-confirmed reset.

Every risk in `unsolved-risks-checklist.md` gets materially worse when a design violates one of these two rules, and every strong point in the ecosystem comparison above comes from enforcing them structurally rather than by convention.
