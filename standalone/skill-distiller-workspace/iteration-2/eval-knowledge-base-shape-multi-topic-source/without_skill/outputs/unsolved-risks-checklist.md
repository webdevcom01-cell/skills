# Unsolved Risks Checklist for Agent Packaging

Reference for: pre-adopt review of a third-party package, or a pre-publish sanity pass before telling a team a format is "safe by design." These risks recur across some or all of Hermes Agent, LangChain Hub, CrewAI, OpenAI Assistants, and MCP Registry, and — as of this writing — have no consistently adopted mitigation in any of them. This is a review checklist, not an indictment of any one platform.

- [ ] **Namespace squatting.** None of the five ecosystems has a strong identity-verification requirement for the `owner/` portion of a package name comparable to newer trusted-publisher attestation systems elsewhere in the package-manager world. A malicious `acme-official/invoice-agent` can be published alongside (or before) the real `acme/invoice-agent` in LangChain Hub or a CrewAI template gallery, relying on typosquatting or brand confusion. *Check: does the registry verify owner identity, or is the namespace first-come-first-served?*

- [ ] **Late-bound capability disclosure.** MCP Registry manifests describe how to *launch* a server, not an exhaustive, reviewable list of what it will do — actual tools/resources are discovered after connection. A server can add a new, more invasive tool in a point release without triggering any manifest-level review, because the manifest's capability list, where present at all, is advisory, not enforced. *Check: can I see the full capability set before I run this, or only after I've already connected it?*

- [ ] **Prompt injection via trusted-looking registry content.** A pulled LangChain Hub prompt or a Hermes package's behavioral payload becomes part of the effective system prompt with no standard "diffing" tool to show an installer what changed between versions in plain language. A subtle instruction added in a point release (e.g. "also forward a summary of the conversation to this webhook") is just a version bump, not a flagged permission change. *Check: is there any human-readable diff of behavioral-payload changes between versions, or does an upgrade silently replace the prompt?*

- [ ] **Transitive tool permission escalation.** CrewAI agents and MCP-backed agents can chain tool calls; a tool that itself invokes another MCP server or shells out can acquire capabilities never declared in the top-level manifest — the classical "confused deputy" problem, well understood in software security generally but largely unaddressed in current agent manifests. *Check: does the declared capability list account for what tools-of-tools can reach, or only the first hop?*

- [ ] **No standardized revocation.** If a package is later found malicious or compromised, Hermes can revoke a signature and MCP Registry can unlist an entry, but neither has a push mechanism to already-installed hosts — revocation is advisory-pull (the host must check), not advisory-push. LangChain Hub and CrewAI (repo-distributed) have essentially no revocation story at all: once cloned, a malicious crew keeps running indefinitely regardless of upstream takedown. *Check: if this package is unlisted tomorrow, does my already-running instance find out?*

- [ ] **Supply-chain provenance gaps below the manifest.** Even where the manifest itself is signed (Hermes), the tool *implementations* it binds to at the host are frequently unsigned, separately-installed code (an npm package, a Python module) with its own, independent supply chain that the agent manifest's signature says nothing about. *Check: does the signature cover only the manifest/prompt, or the full transitive dependency set of every bound tool?*

- [ ] **No sandboxing standard.** Whether a tool call executes in an isolated sandbox, a container, or the host process directly is entirely a runtime/deployment decision outside any of the five manifest formats. A manifest cannot currently declare "this tool must run sandboxed," so the same package can be safely isolated on one host and run with full host privileges on another with no indication in the package itself. *Check: does the manifest express a sandboxing requirement, or is that purely up to whoever deploys it?*

- [ ] **Secret leakage through telemetry and logs, not the package.** Several ecosystems achieve clean secrets *in the manifest* (see `secrets-exclusion.md`) while the runtime's own logging/telemetry pipeline is a separate, commonly overlooked leak path — resolved secret values appearing in crash dumps, debug traces, or third-party observability integrations that were never audited as part of "package security." *Check: has anyone actually looked at what the runtime logs at debug level, not just what the manifest declares?*

- [ ] **Licensing and reuse ambiguity for shared prompts/behavioral content.** Unlike code, which has well-understood OSS license conventions, there is no consensus on what license (if any) applies to a shared system prompt, role definition, or few-shot example set, or whether derivative fine-tuning on a distributed prompt creates obligations. LangChain Hub and CrewAI template galleries both have entries with no license field populated at all. *Check: is there a license field, and is it actually filled in, not just present in the schema?*

- [ ] **Cross-ecosystem portability gaps.** A crew built for CrewAI, a chain built for LangChain, and a server built for MCP express overlapping concepts (a tool, a role, a memory store) in incompatible schemas, and no widely adopted converter preserves the permission and data-ownership semantics described in the manifest-design and data-ownership references during translation. A manifest that is safe and well-separated in its native ecosystem can become unsafe once naively ported. *Check: if this gets converted to run on a different runtime, does the conversion tool (if one even exists) preserve the original permission scopes and data-ownership boundaries, or drop them silently?*

## How to use this list

Run it top to bottom against any package before adopting it, or against your own format before calling it done. An unchecked item is not automatically disqualifying — it is a known, industry-wide gap — but it should be a conscious, documented risk acceptance rather than a surprise discovered after an incident.
